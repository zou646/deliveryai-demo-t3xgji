## 1. 一句话概述

在【沸点火锅点单概念演示（hdl-order-demo）】中新增【积分体系：消费送积分、积分查看、积分使用】，使【顾客】能够【消费后获得积分、查看积分余额与明细、并使用积分抵扣应付金额】，同时【保持纯前端内存态演示形态，不影响现有点单/履约/结账/满减/中英文/老人模式等既有链路】。

## 2. 背景与目标

### 背景
- 概念演示已覆盖「绑定桌台 → 点餐 → 履约 → 结账支付」完整链路（`home → welcome → menu → order → checkout`），但缺少会员激励闭环，积分功能可补齐「消费后沉淀、查看、再消费」的会员运营体验。
- 顶栏已有会员入口（`TopBar` 的「会员与排号」弹窗），展示「金焰会员 · 姚乾」、成长值 2,680、可用权益 4 张券，天然可承接积分余额与明细入口（推断，入口细节待产品 Spec 细化）。
- 结账页已有完整金额链路：菜品小计 → 会员菜品券满减（≥¥100 减 ¥30）→ 应付合计（`CheckoutView.tsx`），积分抵扣可自然接入该链路。

### 目标
- 顾客消费后按「1 元 = 1 积分」（规则见待确认项）正确入账积分，且入账结果可感知。
- 顾客可在产品内查看当前积分余额与积分明细（获取/使用记录）。
- 顾客可使用积分（抵扣/兑换，方式待确认），使用后余额正确扣减且记录可查。
- 保持现有点单、履约、结账、满减、服务呼叫、中英文、老人模式、hash 路由等能力不受影响。

### 不做
- 不做真实支付、真实积分账户/后端 API/数据库（仓库约定：纯前端内存态，`server/` 禁止修改且不参与业务链路）。
- 不做会员等级/成长值联动改造：成长值展示保持现状，仅新增积分相关展示。
- 不做积分商城/第三方权益对接（除非在待确认项中确认「兑换」）。
- 不做跨桌台/跨会话的用户级积分体系（当前应用为内存态、无登录用户体系，刷新即重置）。
- 不做积分过期提醒推送、营销活动等扩展能力（除非确认有效期规则需要）。

## 3. 需求详情

### 用户场景
- 场景一（获取）：顾客在结账页核对账单并确认支付，支付成功后看到本次获得的积分，积分余额同步增加。
- 场景二（查看）：顾客在用餐中或支付后，通过顶栏会员入口（推断）查看积分余额与获取/使用明细。
- 场景三（使用）：顾客在结账页看到可用积分，选择使用积分抵扣，系统实时计算抵扣金额与应付合计，支付后积分扣减并生成使用明细。

### 用户路径

**主流程 A：消费送积分**
1. 用户进入结账页（`#/checkout`），核对菜品小计、满减、应付合计。
2. 用户选择支付方式并点击「确认支付」（现有 `PAY`）。
3. 系统按确认的计分规则计算本次应入账积分（基数与取整待确认）。
4. 支付成功页展示本次实付，并展示「获得 N 积分」及累计余额（文案待确认）。
5. 积分余额增加，积分明细新增一条「获取」记录。

**主流程 B：查看积分**
1. 用户点击顶栏会员入口（推断：沿用现有「会员与排号」弹窗，新增积分区块）。
2. 用户查看当前积分余额与累计数据。
3. 用户进入「积分明细」，按时间倒序查看获取/使用记录（每笔含时间、类型、变动值、说明）。

**主流程 C：使用积分（抵扣，若确认）**
1. 用户在结账页看到可用积分与抵扣开关/输入框（若积分余额不满足门槛则置灰，门槛待确认）。
2. 用户选择使用积分，系统按确认的汇率计算抵扣金额，并实时更新应付合计（不可超过抵扣上限，上限待确认）。
3. 用户确认支付，系统扣减积分并生成「使用」明细。
4. 支付成功页展示抵扣后实付金额。

**异常/回退路径**
- 积分不足或低于使用门槛：抵扣不可用/不可选，展示提示（文案待确认）。
- 支付后发生退菜/退款（现有 `REQUEST_CANCEL` 场景）：按确认的回退规则处理积分（回退/不回退待确认）。
- 刷新页面：内存态数据重置（与现有应用行为一致）。

### 产品规则（原子化；标注「待确认」或「推断」）
- R1 积分获取：每消费 1 元获得 1 积分，入账基数（菜品小计/应付合计/实付金额）与取整方式（向下/四舍五入/向上）待确认。
- R2 入账时点：默认在「支付成功后」入账（推断，与支付闭环一致；是否随退款回退待确认）。
- R3 积分查看：产品内可查看积分余额与获取/使用明细；余额 = 累计获取 − 累计使用 − 累计回退（若启用回退）。
- R4 积分使用：使用方式（抵扣现金 / 兑换权益 / 两者）待确认。
- R5 抵扣汇率、单笔抵扣上限、最低使用门槛：待确认（如「100 积分 = 1 元、上限 50%、无门槛」为推荐默认）。
- R6 积分有效期：永久有效为推荐默认，待确认（备选：年底清零 / 入账后 12 个月滚动过期）。
- R7 积分余额上限：无上限为推荐默认，待确认。
- R8 退款回退：支付后退菜/退款是否按对应金额回退积分待确认。
- R9 数据范围：积分状态为会话/桌台级内存态，刷新即重置，不新增后端存储（推断，遵循仓库「无后端」约定；如采用 localStorage 需遵循 try/catch 降级约定，且属实现细节由技术 Spec 决定）。
- R10 多语言：积分相关文案需 zh/en 双语同步（仓库 i18n 约定）。

### 状态与反馈
- 成功：支付成功页展示「获得 N 积分」；抵扣后应付合计正确更新；余额与明细同步更新。
- 失败：抵扣计算异常/支付失败时保持原账单状态且可重试；积分操作失败不导致余额错乱（内存态一次操作，无中间状态，推断）。
- 空态：积分余额为 0、明细为空时展示空态引导文案；未达抵扣门槛时抵扣入口置灰并提示。
- 无权限：无独立登录/用户体系，不存在角色权限拦截场景（不适用）。
- 异常：积分不足抵扣被拒；余额与明细不一致（理论上不应发生，作为正确性验收点）。
- 保持不变：满减规则、支付方式选择、履约状态机、服务呼叫、中英文切换、老人模式、hash 路由、预览模式等既有行为不受影响。

### 关键文案（推断，待产品 Spec 定稿）
- 支付成功：「获得 {{count}} 积分」/「当前积分 {{count}}」
- 查看入口：「积分」/「积分明细」
- 抵扣：「使用积分抵扣」「可用 {{count}} 积分」「本次抵扣 {{amount}}」
- 空态：「暂无积分记录」等
- 以上需 zh/en 双语同步。

### 关键表现要求
- 需求与视觉强相关度中等：积分入口与积分区块应沿用现有 rice/chili/amber/charcoal 色板、圆角卡片与按钮风格（`tailwind.config.js`、`src/index.css`），具体布局与视觉由产品 Spec/设计稿细化（推断）。

## 4. 约束限制

- 纯前端内存态：无后端 API、无数据库、不修改 `server/`；刷新即重置（仓库 AGENTS.md「不要做」）。
- 不引入额外 UI 库或设计系统框架；不使用 CSS Modules / styled-components。
- i18n：新增文案在 `src/i18n.ts` zh/en 两处同步；新增 localStorage key 一律 try/catch 降级（如采用）。
- 新增独立视图需三处同步：`ViewName` 类型、`useViewRoute` 的 `VIEWS`、对应 `*View.tsx` 组件（如采用独立积分明细视图）。
- 构建/静态检查/E2E 须保持通过：`npm run build`、`npm run lint`、`npx tsc -b --noEmit`、`npx playwright test`。
- 性能/稳定性：内存态小数据量，无额外性能要求；既有 E2E（`view-routing.spec.ts`、`super-spicy.spec.ts`）不得回归。

## 5. 验收标准（待确认后定稿为可执行口径）

- [主流程-获取] 在用户完成支付后，系统应按「1 元 = 1 积分 + 确认的基数/取整规则」正确入账，支付成功页展示本次获得积分，积分余额与明细同步正确。
- [主流程-查看] 在会员入口/积分页面中，用户应看到当前积分余额及每笔获取/使用明细（类型、时间、变动值）。
- [主流程-使用] 在结账页选择使用积分后，应付金额按确认的汇率、上限、门槛正确扣减；支付成功后余额正确扣减且生成使用明细。
- [内容正确性] 积分余额始终等于「累计获取 − 累计使用 − 累计回退（若启用）」，与明细合计一致。
- [异常处理] 积分不足/不满足门槛时抵扣不可用并给出提示；退款/退菜时按确认的回退规则处理积分。
- [边界约束] 本次改动不影响现有点单、履约、结账满减、服务呼叫、中英文、老人模式、hash 路由与既有 E2E 用例。
- [兼容稳定] `npm run build`、`npm run lint` 通过，既有 Playwright 用例保持绿色。
