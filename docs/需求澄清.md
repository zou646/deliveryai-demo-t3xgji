## 1. 一句话概述

在【沸点火锅点单概念演示（hdl-order-demo）】中新增【积分体系：消费送积分、积分查看、积分兑换权益】，使【顾客】能够【消费支付后获得积分、查看积分余额与明细、并使用积分兑换权益】，同时【保持纯前端内存态演示形态，不影响现有点单/履约/结账/满减/中英文/老人模式等既有链路】。

## 2. 背景与目标

### 背景
- 概念演示已覆盖「绑定桌台 → 点餐 → 履约 → 结账支付」完整链路（`home → welcome → menu → order → checkout`），缺少会员激励闭环；积分功能补齐「消费后沉淀 → 查看 → 兑换权益」的会员运营体验。
- 顶栏已有会员入口（`TopBar` 的「会员与排号」弹窗），展示「金焰会员 · 姚乾」、成长值 2,680、可用权益 4 张券（含 ¥30 菜品券），可承接积分余额与明细入口（推断，入口细节待产品 Spec 细化）。
- 结账页已有完整金额链路：菜品小计 → 会员菜品券满减（≥¥100 减 ¥30）→ 应付合计（`CheckoutView.tsx`），积分兑换权益需与该链路衔接。

### 目标
- 顾客消费支付后按「1 元 = 1 积分」正确入账积分（基数=应付合计、向上取整，已确认），入账结果可感知。
- 顾客可在产品内查看当前积分余额与积分明细（获取/使用/回退/过期记录）。
- 顾客可使用积分兑换权益（已确认使用方式为「仅兑换权益」，具体形态待确认），使用后余额正确扣减且记录可查。
- 保持现有点单、履约、结账、满减、服务呼叫、中英文、老人模式、hash 路由等能力不受影响。

### 不做
- 不做真实支付、真实积分账户/后端 API/数据库（仓库约定：纯前端内存态，`server/` 禁止修改且不参与业务链路）。
- 不做「输入式现金抵扣」：积分不直接在结账时按输入金额抵扣现金（负责人已确认使用方式为「仅兑换权益」）。
- 不做会员等级/成长值联动改造：成长值展示保持现状。
- 不做第三方积分商城/外部权益对接。
- 不做跨桌台/跨会话的用户级积分体系（应用为内存态、无登录用户体系，刷新即重置）。
- 不做积分到期提醒推送等扩展能力（有效期规则已确认，展示与提醒方式由产品 Spec 细化）。

## 3. 需求详情

### 用户场景
- 场景一（获取）：顾客在结账页核对账单并确认支付，支付成功后看到本次获得的积分，积分余额同步增加。
- 场景二（查看）：顾客在用餐中或支付后，通过顶栏会员入口（推断）查看积分余额与获取/使用/回退/过期明细。
- 场景三（兑换）：顾客用积分兑换权益（形态待确认），兑换后积分扣减、权益生效、明细可查。

### 用户路径

**主流程 A：消费送积分**
1. 用户进入结账页（`#/checkout`），核对菜品小计、满减、应付合计。
2. 用户选择支付方式并点击「确认支付」（现有 `PAY`）。
3. 系统按「应付合计 × 1 积分/元、向上取整」计算本次应入账积分。
4. 支付成功页展示本次实付与「获得 N 积分」及累计余额。
5. 积分余额增加，积分明细新增一条「获取」记录（含入账时间与到期时间，12 个月滚动有效）。

**主流程 B：查看积分**
1. 用户点击顶栏会员入口（推断：沿用现有「会员与排号」弹窗，新增积分区块）。
2. 用户查看当前积分余额与累计数据。
3. 用户进入「积分明细」，按时间倒序查看记录：类型（获取/使用/回退/过期）、时间、变动值、说明、到期时间（如有）。

**主流程 C：使用积分（兑换权益，形态待确认）**
1. 用户进入兑换入口（推断：会员弹窗内「积分兑换」或结账页兑换区，入口待产品 Spec 细化）。
2. 用户看到可兑换权益清单与所需积分（形态待确认）。
3. 用户选择兑换，系统校验积分余额（无最低门槛）与兑换上限（权益价值不超过应付合计 50%，若为当餐抵扣形态）。
4. 兑换成功：积分扣减、生成「使用/兑换」明细、权益生效。
5. 若为当餐抵扣形态：结账应付金额按兑换权益价值扣减（与满减叠加关系待确认）。

**异常/回退路径**
- 积分余额不足：兑换不可用/校验失败并提示（文案待确认）。
- 积分过期：过期积分不可用，明细中展示过期记录（推断）。
- 支付后退菜/退款：按对应金额回退积分并记录「回退」明细（已确认）。
- 刷新页面：内存态数据重置（与现有应用行为一致）。

### 产品规则（已确认项标「已确认」，其余标「待确认/推断」）

- R1 积分获取（已确认）：每消费 1 元获得 1 积分；计分基数 = 应付合计（菜品小计 − 满减），积分抵扣/兑换不参与计分基数（以支付时的应付合计为准）；取整方式 = 向上取整（如应付 ¥128.5 → 129 积分）。
- R2 入账时点（已确认）：支付成功后入账。
- R3 积分查看：产品内可查看积分余额与明细；余额 = 累计获取 − 累计使用（兑换）− 累计回退 − 累计过期。
- R4 积分使用方式（已确认）：仅兑换权益，不做输入式现金抵扣。
- R5 兑换价值（已确认口径，与原抵扣选项一致）：100 积分 = 1 元，作为兑换权益的价值换算基准。
- R6 兑换上限与门槛（已确认口径）：单笔兑换权益价值不超过应付合计 50%；无最低使用门槛。
- R7 有效期（已确认）：每笔积分自入账起 12 个月滚动有效，到期自动过期；过期处理与展示方式待产品 Spec 细化（推断：明细中带到期时间与过期记录）。
- R8 退款回退（已确认）：支付后入账；退菜/退款按对应金额回退积分并记录回退明细。
- R9 兑换权益形态（待确认）：兑换为「当餐抵扣权益」/「优惠券包」/ 其他，直接影响主流程 C 与验收标准。
- R10 兑换与满减叠加（待确认）：兑换权益与现有「会员菜品券满减 ≥¥100 减 ¥30」是否可叠加、叠加计算顺序。
- R11 数据范围（推断）：积分状态为会话/桌台级内存态，刷新即重置，不新增后端存储；如采用 localStorage 需遵循 try/catch 降级约定（实现细节由技术 Spec 决定）。
- R12 多语言（仓库约定）：积分相关文案 zh/en 双语同步。

### 状态与反馈
- 成功：支付成功页展示「获得 N 积分」；兑换成功提示与余额更新；明细同步更新。
- 失败：兑换校验失败（余额不足/超过上限）时提示并可重试；支付失败保持原账单状态。
- 空态：积分余额为 0、明细为空时展示空态引导；无可兑换权益或权益已兑完时展示对应空态。
- 无权限：无独立登录/用户体系，不存在角色权限拦截场景（不适用）。
- 异常：积分不足兑换被拒；退款回退积分；过期积分不可用。
- 保持不变：满减规则、支付方式选择、履约状态机、服务呼叫、中英文切换、老人模式、hash 路由、预览模式等既有行为不受影响。

### 关键文案（推断，待产品 Spec 定稿）
- 支付成功：「获得 {{count}} 积分」/「当前积分 {{count}}」
- 查看入口：「积分」/「积分明细」
- 兑换：「积分兑换」「可用 {{count}} 积分」「兑换需 {{count}} 积分」「本次兑换权益价值 {{amount}}」
- 过期/回退：「已于 {{date}} 过期」「退款回退 {{count}} 积分」

### 关键表现要求
- 需求与视觉强相关度中等：积分入口与积分区块应沿用现有 rice/chili/amber/charcoal 色板、圆角卡片与按钮风格（`tailwind.config.js`、`src/index.css`），具体布局与视觉由产品 Spec/设计稿细化（推断）。

## 4. 约束限制

- 纯前端内存态：无后端 API、无数据库、不修改 `server/`；刷新即重置（仓库 AGENTS.md「不要做」）。
- 不引入额外 UI 库或设计系统框架；不使用 CSS Modules / styled-components。
- i18n：新增文案在 `src/i18n.ts` zh/en 两处同步；新增 localStorage key 一律 try/catch 降级（如采用）。
- 新增独立视图需三处同步：`ViewName` 类型、`useViewRoute` 的 `VIEWS`、对应 `*View.tsx` 组件（如采用独立积分明细/兑换视图）。
- 构建/静态检查/E2E 须保持通过：`npm run build`、`npm run lint`、`npx tsc -b --noEmit`、`npx playwright test`。
- 性能/稳定性：内存态小数据量，无额外性能要求；既有 E2E（`view-routing.spec.ts`、`super-spicy.spec.ts`）不得回归。

## 5. 验收标准

- [主流程-获取] 在用户完成支付后，系统应按「应付合计（满减后）× 1 积分/元、向上取整」正确入账；支付成功页展示本次获得积分；积分余额与获取明细（含到期时间）同步正确。
- [主流程-查看] 在会员入口/积分页面中，用户应看到当前积分余额及每笔获取/使用/回退/过期明细（类型、时间、变动值）。
- [主流程-兑换] 用户按确认的兑换规则（价值 100 积分=1 元、单笔上限应付 50%、无门槛）完成兑换后，积分余额正确扣减、权益生效、明细新增兑换记录；若为当餐抵扣形态，应付金额按规则正确更新。
- [内容正确性] 积分余额始终等于「累计获取 − 累计使用（兑换）− 累计回退 − 累计过期」，与明细合计一致。
- [异常处理] 积分余额不足/过期时兑换不可用并给出提示；支付后退菜/退款时按对应金额回退积分并记录回退明细。
- [边界约束] 本次改动不影响现有点单、履约、结账满减、服务呼叫、中英文、老人模式、hash 路由与既有 E2E 用例。
- [兼容稳定] `npm run build`、`npm run lint` 通过，既有 Playwright 用例保持绿色。

## 6. 待确认清单

- 已确认（负责人 ask-user-interaction 答复）：
  1. 使用方式 = 仅兑换权益。
  2. 计分基数 = 应付合计（满减后、兑换前）；取整 = 向上取整。
  3. 入账时点 = 支付后入账；退菜/退款按对应金额回退积分。
  4. 兑换价值 = 100 积分 = 1 元；单笔上限 = 应付合计 50%；无最低门槛。
  5. 有效期 = 自入账起 12 个月滚动有效。
- 冲突信息：
  - 使用方式确认「仅兑换权益」，但同步确认的「100 积分=1 元、上限 50%、无门槛」是原「抵扣」口径的规则。本文档已将其解释为「兑换价值基准 + 单笔兑换上限」（R5/R6），是否完全符合负责人意图取决于 R9 兑换形态的确认；若负责人期望的是「当餐直接抵扣」，需在下一轮确认中更正使用方式。
- 缺失信息（待补充确认后定稿）：
  - R9 兑换权益的具体形态（当餐抵扣权益 / 优惠券包 / 其它）。
  - R10 兑换权益与现有「会员菜品券满减」的叠加关系与计算顺序。
  - 兑换操作入口与触发时点（会员弹窗 / 独立兑换视图 / 结账页）。
  - 过期积分的展示与提示方式。
- 推断项：查看入口沿用顶栏会员弹窗、兑换在结账页选择并即时生效（若为当餐抵扣形态）、积分账户为会话/桌台级内存态、视觉风格沿用现有色板——若与负责人意图不符请在确认时指出。
