# Review Summary

- 本次需求: 在沸点火锅点单概念演示中新增积分体系——消费支付送积分（1 元 = 1 积分）、会员弹窗查看积分余额与明细、积分兑换固定面值菜品券并在结账时与会员菜品券满减叠加抵扣。
- 需求类型: UX / frontend（页面、入口、状态、文案、交互）+ 数据模型（会话级内存态积分账户 / 明细 / 兑换券）
- 变更面: Functional Requirements（REQ-001~009）、UX Design（会员弹窗积分区、积分明细、积分兑换、结账页券选用、支付成功反馈）、Backend/Data（内存态数据模型、状态流转、取整 / 上限 / 有效期规则）; 不涉及: API Design（无对外 API/SDK）、Metrics（演示项目无埋点体系）、真实支付 / 后端 / 存储; 待确认: 兑换档位表数值、退款回退取整与触发路径、券多选与 50% 上限截断细节、过期演示方式、存储形态（本文档已给出建议默认值，需评审复核）
- 变更面判断依据: 需求澄清定稿 v1.0（docs/需求澄清.md，R1–R12）; 仓库证据: src/components/TopBar.tsx（会员弹窗）、src/components/CheckoutView.tsx（金额链路 小计 − 满减 − 应付）、src/state/orderReducer.ts（PAY / RESET / REQUEST_CANCEL）、src/types.ts（AppState / AppAction）、src/App.tsx、src/i18n.ts、src/hooks/useViewRoute.ts
- 差异判断: 产品形态差异: 涉及——纯前端内存态概念演示（无登录用户体系、刷新即重置、无后端/数据库），不适用生产化会员/积分账户、跨会话持久化或用户级归属; 站点 / 环境 / 版本差异: 不涉及——单仓库、单 GitHub Pages 部署环境、无地域 / 灰度差异; 依据: 仓库 AGENTS.md「不引入后端 API 调用，所有数据为前端内存态」、knowledge/context 项目地图与系统架构
- 本次变更关键信息:
  - 新增会话级内存态积分体系：支付成功按「应付合计（满减后、兑换前）× 1 积分/元、向上取整」入账；支付成功页展示本次获得积分与累计余额。
  - 会员弹窗新增积分区块：积分余额展示、积分明细（获取 / 使用 / 回退 / 过期，时间倒序，含到期时间）、积分兑换区（默认档位 500 = ¥5 / 1000 = ¥10 / 2000 = ¥20 菜品券，兑换无最低门槛）。
  - 结账页新增兑换券选用：支持多选，应付 = 菜品小计 − 会员菜品券满减 − 兑换券价值；当餐兑换券抵扣总额不超过「兑换前应付合计（小计 − 满减）」的 50%（超出截断、不找零、不产生负应付）。
  - 兑换券抵扣不影响本次积分入账基数（计分基数 = 兑换前应付合计）。
  - 退款 / 退菜确认后按对应金额回退积分并记录「回退」明细；每笔积分自入账起 12 个月滚动有效，到期自动移出余额并记录「过期」明细，过期积分不可兑换。
  - 范围决策: 不新增独立视图 / hash 路由（积分明细与兑换均置于会员弹窗内），最小侵入保持既有路由与 E2E 稳定；默认不引入 localStorage（内存态，刷新即重置）。
  - 重要风险 / 待确认: 兑换档位表数值、退款回退取整与触发路径（现有 REQUEST_CANCEL 仅到 requested）、券多选与 50% 上限截断细节、过期积分演示方式、存储形态——均已给出建议默认值，需评审复核。
- Review 重点:
  - scope: 三条主流程（获取 / 查看 / 兑换 + 结账叠加）是否完整覆盖任务与澄清文档 R1–R12
  - REQs: 每条独立可测，重要验收使用 EARS，重要场景使用 Gherkin

  - 兼容性: 既有 hash 路由、i18n、老人模式、E2E（view-routing / super-spicy）不回归
  - 差异: 内存态概念演示边界是否始终明确（不引入后端 / 持久化 / 用户体系 / 真实支付）

# Spec: 积分功能（消费送积分 / 查看积分 / 兑换菜品券）

- **需求来源**: 任务描述「新增积分功能：消费送积分、查看积分、使用积分」；需求澄清 v1.0 定稿（docs/需求澄清.md，两轮 ask-user-interaction 确认 7 项业务规则）。

## 3. Glossary

| 概念 / 术语 | 描述 | 备注 |
|-------------|------|------|
| 积分（Points） | 顾客消费支付后获得的虚拟激励单位，1 元 = 1 积分 | 会话级内存态 |
| 计分基数（Points Base） | 本次入账积分的计算基数 = 应付合计（菜品小计 − 会员菜品券满减，兑换券抵扣前） | 澄清 R1 / R2 确认 |
| 积分明细（Points Ledger） | 每笔积分变动的流水记录：类型、时间、变动值、说明、到期时间（如有） | 类型 = 获取 / 使用 / 回退 / 过期 |
| 兑换券（菜品券，Redeemed Coupon） | 用户用积分兑换的固定面值菜品券，可当餐结账抵扣 | 形态 = 优惠券包（澄清 R4 / R9） |
| 可用权益（Available Benefits） | 会员弹窗中的权益展示，含静态 4 张券与积分兑换券 | 兑换券在结账页可选用 |
| 应付合计（Payable） | 结账金额口径：菜品小计 − 会员菜品券满减 − 兑换券价值 | 兑换券使用后 |
| 积分回退 | 支付后退款 / 退菜确认后按对应金额回退积分并记录「回退」明细 | 澄清 R8 |
| 积分过期 | 每笔积分自入账起 12 个月滚动有效，到期自动过期 | 澄清 R7 |

## 4. Functional Requirements

### REQ-001: 消费支付送积分（获取）

**User Story**
> As a 顾客, I want 支付成功后获得积分, so that 消费得到即时激励与留存感知。

**Priority**: P0

**需求描述**
用户进入结账页（`#/checkout`），核对账单（菜品小计、会员菜品券满减、应付合计），选择支付方式后点击「确认支付」。系统在支付成功后按计分规则入账积分，并在支付成功页反馈本次获得积分与累计余额。

**Acceptance Requirements (EARS)**
- **REQ-001.1**: The system **shall** 在支付成功后，按「计分基数 = 应付合计（菜品小计 − 会员菜品券满减，兑换券抵扣前）× 1 积分/元、向上取整」计算并入账本次积分。
- **REQ-001.2**: When 支付成功, the system **shall** 在支付成功页展示「获得 N 积分」与当前积分余额。
- **REQ-001.3**: If 应付合计 ≤ 0 或未发生支付, then the system **shall** 不入账积分。
- **REQ-001.4**: If 应付合计为 ¥128.5, then the system **shall** 向上取整入账 129 积分。
- **REQ-001.5**: If 已处于支付成功（paid）状态, then the system **shall** 不重复入账积分（会话内单次支付幂等）。

**Gherkin**
```gherkin
Scenario: 支付成功后按规则入账积分
  Given 本桌订单已完成并进入结账页
  And 菜品小计 ¥158.5、会员菜品券满减 ¥30、未使用兑换券
  When 用户选择支付方式并点击「确认支付」
  Then 系统按 128.5 × 1 = 128.5 向上取整入账 129 积分
  And 支付成功页展示「获得 129 积分」与累计余额
  And 积分明细新增一条「获取」记录（含入账时间与到期时间）
```

**用户交互**

| 步骤 | 用户动作 | 产品响应 |
|------|----------|----------|
| 1 | 核对账单（小计 / 满减 / 应付） | 展示金额明细（沿用现有结账页） |
| 2 | 选择支付方式（移动支付 / 桌边 POS） | 高亮所选方式（沿用现有） |
| 3 | 点击「确认支付 {{amount}}」 | 支付成功；按规则入账积分 |
| 4 | 查看支付成功页 | 展示本次实付、「获得 N 积分」、当前积分余额 |

### REQ-002: 积分查看（余额与明细）

**User Story**
> As a 顾客, I want 查看积分余额与明细, so that 了解积分的来龙去脉与可用状态。

**Priority**: P0

**需求描述**
用户通过顶栏会员入口（会员与排号弹窗）查看当前积分余额，并可进入「积分明细」按时间倒序查看每笔记录；明细区分获取 / 使用 / 回退 / 过期四种类型，包含时间、变动值与说明。

**Acceptance Requirements (EARS)**
- **REQ-002.1**: The system **shall** 在顶栏会员弹窗展示当前积分余额。
- **REQ-002.2**: When 用户进入「积分明细」, the system **shall** 按时间倒序展示每笔记录：类型（获取 / 使用 / 回退 / 过期）、发生时间、变动值、说明、到期时间（获取类记录如有）。
- **REQ-002.3**: When 积分明细为空, the system **shall** 展示空态引导（如「暂无积分记录」）。
- **REQ-002.4**: The system **shall** 保证展示余额与明细合计一致（见 REQ-007）。

**用户交互**

| 步骤 | 用户动作 | 产品响应 |
|------|----------|----------|
| 1 | 点击顶栏会员入口 | 会员弹窗展示积分余额与「积分明细」「积分兑换」入口 |
| 2 | 点击「积分明细」 | 弹窗内展示明细列表（时间倒序） |
| 3 | 查看单笔记录 | 展示类型徽标、变动值（±N）、时间、说明、到期时间（如有） |

### REQ-003: 积分兑换菜品券（使用）

**User Story**
> As a 顾客, I want 用积分兑换菜品券, so that 积分能转化为实际用餐权益。

**Priority**: P0

**需求描述**
用户进入会员弹窗「积分兑换」区，查看可兑换券档位与当前积分余额；选择某档位兑换后，系统校验余额充足则扣减积分、生成「使用」明细、并将对应面值菜品券加入可用权益；余额不足时兑换不可用并提示。

**Acceptance Requirements (EARS)**
- **REQ-003.1**: The system **shall** 提供固定面值兑换档位，兑换价值按「100 积分 = 1 元」换算（默认档位：500 积分 = ¥5 券、1000 积分 = ¥10 券、2000 积分 = ¥20 券，数值待评审复核，见 OQ-001）。
- **REQ-003.2**: The system **shall** 允许余额达到档位所需积分即可兑换（无最低兑换门槛、无使用次数限制，受当餐抵扣上限约束见 REQ-004）。
- **REQ-003.3**: When 用户选择某档位兑换, the system **shall** 校验当前积分余额 ≥ 该档位所需积分；余额不足时兑换不可用并提示（如「积分不足」）。
- **REQ-003.4**: When 兑换成功, the system **shall** 扣减对应积分、新增一条「使用」明细（变动值 −N）、并将等面值菜品券加入可用权益。
- **REQ-003.5**: When 积分余额为 0 或无可用兑换档位, the system **shall** 展示空态提示（如「暂无可用积分」）。

**Gherkin**
```gherkin
Scenario: 积分充足时兑换成功
  Given 用户当前积分余额为 1200
  When 用户选择「1000 积分 = ¥10 菜品券」并确认兑换
  Then 系统扣减 1000 积分，余额变为 200
  And 可用权益新增一张 ¥10 菜品券
  And 积分明细新增一条「使用 −1000」记录

Scenario: 积分不足时兑换被拒
  Given 用户当前积分余额为 300
  When 用户选择「500 积分 = ¥5 菜品券」
  Then 兑换不可用并提示「积分不足」
  And 积分余额与明细均不发生变化
```

**用户交互**

| 步骤 | 用户动作 | 产品响应 |
|------|----------|----------|
| 1 | 进入会员弹窗「积分兑换」区 | 展示当前积分余额与可兑换档位（面值 / 所需积分） |
| 2 | 选择某档位 | 校验余额；不足则禁用并提示 |
| 3 | 确认兑换 | 成功：余额扣减、券入可用权益、明细新增「使用」记录、成功反馈 |

### REQ-004: 结账使用兑换券叠加抵扣

**User Story**
> As a 顾客, I want 结账时使用兑换券抵扣, so that 积分兑换的权益在当餐真正生效。

**Priority**: P0

**需求描述**
结账页新增「可用兑换券」区块，展示本单可用的积分兑换券；用户可勾选一张或多张，系统按叠加规则实时重算应付金额；兑换券抵扣与现有会员菜品券满减可叠加，且当餐抵扣总额不超过「兑换前应付合计」的 50%。

**Acceptance Requirements (EARS)**
- **REQ-004.1**: The system **shall** 在结账页展示本单可用兑换券（张数与总价值），仅列出来源为积分兑换的券。
- **REQ-004.2**: When 用户勾选兑换券, the system **shall** 按「应付 = 菜品小计 − 会员菜品券满减 − 兑换券价值」实时重算应付金额。
- **REQ-004.3**: When 当餐兑换券抵扣总额超过兑换前应付合计（菜品小计 − 会员菜品券满减）的 50%, then the system **shall** 按 50% 上限截断抵扣并提示（超出部分不可用）。
- **REQ-004.4**: If 兑换券价值大于抵扣上限或应付抵扣后小于 0, then the system **shall** 按上限截断，不产生负应付、不找零。
- **REQ-004.5**: The system **shall** 保证兑换券抵扣不影响本次积分入账基数（计分基数 = 兑换前应付合计，见 REQ-001.1）。

**Gherkin**
```gherkin
Scenario: 兑换券与满减叠加抵扣
  Given 菜品小计 ¥158.5、会员菜品券满减 ¥30、兑换前应付合计 ¥128.5
  And 用户持有一张 ¥10 兑换券
  When 用户在结账页勾选该兑换券
  Then 应付金额 = 158.5 − 30 − 10 = ¥118.5
  And 兑换券抵扣 10 未超过 128.5 × 50% = 64.25，全部可用

Scenario: 抵扣超过 50% 上限时截断
  Given 菜品小计 ¥80、无满减、兑换前应付合计 ¥80
  And 用户持有 ¥20 与 ¥30 兑换券各一张
  When 用户勾选两张券（合计 ¥50）
  Then 系统按 80 × 50% = ¥40 上限截断，实际抵扣 ¥40，应付 ¥40
  And 提示超出部分不可用
```

**用户交互**

| 步骤 | 用户动作 | 产品响应 |
|------|----------|----------|
| 1 | 进入结账页 | 展示金额明细与「可用兑换券」区块（张数 / 总价值） |
| 2 | 勾选一张或多张兑换券 | 应付金额实时更新，抵扣明细行展示「使用兑换券 −¥X」 |
| 3 | 超出 50% 上限的勾选 | 按上限截断并提示，允许用户调整勾选 |
| 4 | 点击「确认支付」 | 按最终应付支付并触发积分入账（基数不变） |

### REQ-005: 退款 / 退菜回退积分

**User Story**
> As a 门店, I want 支付后退菜 / 退款时按对应金额回退积分, so that 积分与消费金额保持一致、避免多给积分。

**Priority**: P1

**需求描述**
支付成功后，若订单项退菜 / 退款被确认，系统按该菜品对应金额回退已入账积分，并新增「回退」明细。

**Acceptance Requirements (EARS)**
- **REQ-005.1**: When 已支付订单中某项退菜 / 退款被确认, the system **shall** 按该菜品金额（含其占计分基数的部分）回退对应积分并新增「回退」明细。
- **REQ-005.2**: The system **shall** 保证回退后积分余额不为负（不足 0 时按 0 截断并提示）。
- **REQ-005.3**: If 未支付订单发生退菜 / 退款, then the system **shall** 不涉及积分回退（积分尚未入账）。

**用户交互**

| 步骤 | 用户动作 | 产品响应 |
|------|----------|----------|
| 1 | 支付后在订单页对某菜品发起退菜申请（沿用现有 REQUEST_CANCEL） | 申请状态 = requested（沿用现有） |
| 2 | 退菜申请被确认（演示触发方式见 OQ-002） | 积分按对应金额回退，「回退」明细新增，余额更新 |

### REQ-006: 积分过期处理

**User Story**
> As a 顾客, I want 了解积分到期时间, so that 在有效期内使用积分、避免过期损失。

**Priority**: P1

**需求描述**
每笔获取的积分自入账起 12 个月滚动有效；到期后自动从可用余额剔除，并生成「过期」明细记录；过期积分不可用于兑换。演示会话通常短于有效期，本规则以保证展示正确性为主（演示触发方式见 OQ-004）。

**Acceptance Requirements (EARS)**
- **REQ-006.1**: The system **shall** 为每笔获取积分记录到期时间 = 入账时间 + 12 个月，并在明细中展示。
- **REQ-006.2**: When 某笔积分到达到期时间, the system **shall** 将其从可用余额剔除并新增「过期」明细记录。
- **REQ-006.3**: The system **shall** 保证过期积分不可用于兑换（兑换时仅以可用余额校验）。

### REQ-007: 积分余额一致性

**User Story**
> As a 系统, I want 积分余额恒等于明细合计, so that 用户看到的数据自洽可信。

**Priority**: P0

**需求描述**
积分余额由明细流水推导，任何入账 / 兑换 / 回退 / 过期操作都同时更新余额与明细，保证「余额 = 累计获取 − 累计使用（兑换）− 累计回退 − 累计过期」。

**Acceptance Requirements (EARS)**
- **REQ-007.1**: The system **shall** 保证积分余额始终等于「累计获取 − 累计使用（兑换）− 累计回退 − 累计过期」。
- **REQ-007.2**: When 任何积分变动发生时, the system **shall** 在同一操作中同步更新余额与明细，保证二者合计一致。
- **REQ-007.3**: When 用户在查看积分余额与明细时, the system **shall** 展示一致的余额口径（不含过期积分）。

### REQ-008: 空态与异常提示

**User Story**
> As a 顾客, I want 在边界与异常场景得到明确反馈, so that 知道发生了什么以及下一步怎么做。

**Priority**: P1

**需求描述**
覆盖空态与异常提示：无积分记录、无可用券、积分不足、抵扣超上限、兑换成功 / 回退成功等反馈。

**Acceptance Requirements (EARS)**
- **REQ-008.1**: When 积分明细为空, the system **shall** 展示空态（如「暂无积分记录」）。
- **REQ-008.2**: When 可用兑换券为空, the system **shall** 在结账页隐藏或置灰券选用区并说明（如「暂无可用兑换券」）。
- **REQ-008.3**: When 兑换校验失败（余额不足 / 未达档位）, the system **shall** 阻止兑换并给出可理解的提示。
- **REQ-008.4**: When 兑换券抵扣触发 50% 上限截断, the system **shall** 提示超出部分不可用，并允许用户调整选择。

### REQ-009: 多语言与文案

**User Story**
> As a 国际用户, I want 积分相关文案中英文一致, so that 切换语言后体验不中断。

**Priority**: P1

**需求描述**
新增积分 / 明细 / 兑换 / 券选用 / 空态 / 提示等文案在 `src/i18n.ts` 的 zh / en 两处同步新增，跟随现有语言切换即时生效。

**Acceptance Requirements (EARS)**
- **REQ-009.1**: The system **shall** 为本次新增的所有用户可见文案提供 zh / en 双语资源，且两组文案语义一致。
- **REQ-009.2**: When 用户切换语言, the system **shall** 使积分相关页面 / 弹窗 / 提示即时切换且不出现缺失 key。

### 6.4 计算规则（技术实现参考）

- **入账**：`earned = ceil(应付合计(小计 − 满减, 兑换前) × 1)`；`应付合计 ≤ 0` 不入账。
- **兑换**：`兑换后余额 = 余额 − 档位积分`；`档位积分 × 0.01 = 券面值（元）`（100 积分 = 1 元）。
- **结账叠加**：`应付 = 小计 − 满减 − 券抵扣`；`券抵扣 = min(用户勾选券价值合计, 兑换前应付合计 × 50%)`；结果 ≥ 0（不找零、不产生负应付）。
- **回退**：`回退积分 = 退款金额对应积分`（取整规则建议与入账一致，向上取整；见 OQ-002），回退后余额按 0 截断。
- **过期**：`到期时间 = 入账时间 + 12 个月`；可用余额计算时剔除 `expiresAt < now` 的获取记录，并生成「过期」明细。
- **一致性**：`余额 = 累计获取 − 累计使用（兑换）− 累计回退 − 累计过期`（REQ-007）。

### 6.5 幂等与防重复

- 支付入账以 `paid` 状态为幂等键：已 paid 不再重复入账（REQ-001.5）。
- 兑换 / 勾选券为即时内存操作，无并发；重复点击以余额 / 券状态实时校验兜底。

### 6.6 存储与生命周期

- **默认内存态**：积分 / 明细 / 券为会话级，刷新即重置（与现有应用一致），不新增 localStorage（OQ-005）。
- 如技术 Spec 评估需跨刷新保留，允许按 R11 在 try/catch 降级约定内引入 localStorage；不得影响现有 `i18nextLng` / `elderly-mode` 行为。
- 不修改 `server/`，不引入后端调用。
